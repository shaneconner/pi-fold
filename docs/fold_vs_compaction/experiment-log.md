# Fold vs. Compaction: Experiment Log

Running log of the pi-fold measurement campaign. This is the groundwork document for the public write-up (Zenodo record plus articles); style rules for anything lifted from here: no em dashes, agent-first framing (self-governance is the product, the automatic ladder is the fallback).

- Package under test: [pi-fold](https://github.com/shaneconner/pi-fold), 75 gates in `tests/verify.mjs`. There is one copy of the runtime on the measurement machine, in this repo. The interactive deployment at `~/.pi/agent/extensions/pi-fold` imports it rather than holding a copy, and the experiment pins every file under `extensions/`, so what runs, what is attested and what is gated are the same bytes.
- Harness: `scripts/*pi_context_experiment*` in the pi-fold repo (moved out of quorum on 2026-08-07), derived from the soak lineage (external pacing, one real Pi session per run, one user message, hash-chained ledgers, artifact-only adjudication, blind grading with separated key). 27 offline verification gates.
- Campaign state: `~/pi-fold-runs/state/ops/pi-context-experiment/` for runs from 2026-08-07 onward. Every rep sealed before that date lives in the frozen quorum-era corpus and pins a quorum `codeCommit`; the two are not one series, and the boundary is recorded below.

## Sealed corpus: extracted, archived, and taken offline (2026-08-07)

The quorum-era corpus could not be moved. Its run configs carry absolute plan paths, its worker reports carry absolute session files, and `run-config.json` is itself hash-sealed inside the candidate artifacts, so no path rewrite survives its own seal. It was therefore read where it stood and reduced in two steps.

First, uniformity. The corpus had been adjudicated by four different adjudicator versions, with only two of nine luna runs on the current one, so a pooled number across it would have been pooling measurements that were not taken the same way. All 17 sealed runs were re-adjudicated under one adjudicator (`ce184531`), non-destructively, as sidecars beside untouched originals. `scripts/grade_pi_context_experiment.mjs` now refuses a campaign that mixes adjudicator versions, so this cannot silently recur.

Second, extraction. `scripts/extract_campaign_metrics.mjs` lifted every metric into `campaign-metrics.json` (17 runs, 3 campaigns, both metric lenses per run, no absolute paths). That file, not the trees, is what the write-up cites.

The four state trees were then archived and removed from the machine's shared run directory. Verified restorable before deletion.

## Condition boundary: the runtime moved, and the context tool was renamed (2026-08-07)

Runs from this date forward are not directly comparable to the archived corpus, and the reason is worth stating plainly rather than burying in a commit.

The harness used to load the runtime under measurement out of a consumer's deployed copy. That was wrong on its own terms: the measured bytes were untracked, so a run's `codeCommit` attested the harness while the code actually executing floated free of it. The runtime now comes from `extensions/` in this repo, and the seal pins every source file under that root. This is a strictly better attestation and changes no behavior.

The rename does change one thing the model sees. The context tool was `quorum_context` and is now `pi_fold_context`; entry types moved from `quorum-active-context-*` to `pi-fold-active-context-*`. Tool names appear in the schema the model is given and inside the runtime's own guidance strings ("Expand exactly: ..."), so this is a small change to the prompt surface, not a pure refactor. It is not expected to matter, but it was not measured, so it is recorded as a boundary rather than assumed away.

Everything else about the pifold arm is held: the same registration options, the same guidance profiles, and no summarizer, which is what `summarizer: "deterministic"` means in this runtime. The tool surface the model sees is unchanged in size and shape (`read`, `repo_stage`, and the context tool), because the exposed set is pinned explicitly by the worker rather than inherited from whatever happens to be registered.

Practical consequence: treat post-2026-08-07 reps as a new campaign. Pooling them with the archived corpus would mix a tool-name change and a different `codeCommit` lineage into whatever effect is being claimed.

## Hypothesis

On long-running work that keeps returning to the same material, agent-governed lossless folding beats stop-the-world compaction on recall and total cost, and locates the window wall that an unmanaged session hits. Headline claim shape: savings at equal or better accuracy.

## Design (ratified 2026-08-05)

Three arms, same model (`openai-codex/gpt-5.6-sol`, xhigh, maxTokens 16,384), same pinned workload, same wall-clock window per repetition wave; repetitions serial so time-of-day varies across reps and not across arms.

| Arm | Active-context runtime | Native auto-compaction |
| --- | --- | --- |
| pifold | on | off |
| native | off | on |
| unmanaged | off | off (terminates at the window wall; the wall is its datum) |

Workload: staged repo-comprehension marathon over curl pinned at `133785b15936` (474 files, 6.2M chars). 64 stages, ~3.83M unique payload chars, seed `aa18d4da8ac01229fdc3475b8ab99f84`, plan sha `6ed7c5f9...`. Stages read broadly, revisit earlier files without resending bytes (so any repeated ingestion is model-initiated by construction), and produce cross-referencing deliverables. Recall probes at stages 16/32/48/64 with mechanically extracted ground truth that never reaches the session.

Metrics per run, all from artifacts: provider-reported usage split cached/fresh/output; reread tax (content-hash repeats of tool results); stop-the-world events and time-to-first-productive-request; recall probe verdicts and deliverable scores (blind-graded, `gpt-5.6-terra` medium, labels/ids/order separated from the packet); voluntary-fold share and curation verb counts; overflow point (unmanaged).

## Harness integrity findings (smoke + rep 1, 2026-08-05)

Nine defects found by live fire and fixed before the sealed rep-1 runs; the measurement pipeline itself (probes, grading, ledgers) worked on the first try. The full list lives in the wiki (`fold-vs-compaction_harness`, "Live-fire lessons"). Highlights that shaped the results:

1. Sessions must expose only the allowed tools; asserting presence is not restriction.
2. The dual tool-result ledgers must be compared as a multiset (concurrent calls interleave differently in completion vs. call order).
3. Probe extraction must anchor on lines that open a definition, not C parameter-list uses (caught by the blind grader disagreeing with every arm).
4. A stale stage key is behavior, not an integrity breach: under pressure the stage nonce gets folded or compacted away, and recovering it is part of what the experiment measures. Budgeted, then latched.
5. The native arm surfaces a full window as a provider error, then compacts and retries; these breaths are stop-the-world data, not failures. Budgeted, then latched.
6. The run seal pins the experiment file set byte-for-byte, not the repo head (concurrent unrelated commits must not void runs).

### What rep 1 establishes

- **Capability**: both managed arms complete a workload that kills an unmanaged session at stage 24 of 64. The wall is real and measured (~1.5M payload chars against a 272k window).
- **Recall**: pi-fold leads, 10/12 vs 7/12 correct. The native arm's three compactions cost it early-session facts outright: three probe answers were absent, not wrong. Lossless recovery (peek/expand) kept every fact reachable in the pifold arm. Observational bonus: in a voided attempt, the pifold agent lost a chained stage nonce to a fold, received an error, recovered the nonce by peeking the fold, and finished all 64 stages.
- **Stop-the-world**: native pays three ~50-second freezes plus re-orientation output (2.8x output tokens). pi-fold folds in stride, zero pauses.
- **Cache economics (the negative finding)**: pi-fold's per-turn fold mutations invalidated the provider prefix cache nearly every request (65 of 94 requests under 10% cached in the observational run; median request 0% cached), paying ~14M fresh input tokens vs native's ~1.3M. Provider caches replay the longest byte-identical prefix; any mid-window edit invalidates everything after it by construction (causal attention), so the cost of a fold equals the bytes after its position, and per-turn folding never lets the cache re-form. Native compaction's three-mutations-per-run rhythm is accidentally near-optimal on this axis.
- Reread tax was negligible for all arms on this reading-heavy workload; the token story is entirely the cache mix.

## Round-2 design: mark-then-commit (ratified 2026-08-05)

Two-phase folding that keeps the agent responsible and adopts only compaction's rhythm, not its lossyness:

- **Mark** is free and continuous: agent and ladder record fold intentions in state; no projection bytes move, no cache dies.
- **Commit** is one batched rewrite, triggered by the pressure threshold or by the agent as a first-class action. Each commit has a target (percent of window freed or span count); if agent marks cover 3 of a target 5, the ladder tops up with the stalest unprotected tool batches. Agent judgment leads, automation guarantees the floor.
- Geometry: tail-adjacent folds are nearly free (little follows them) and may be exempt from batching; deep retroactive folds are the expensive class and belong in the rare epochs; expands can ride a commit epoch. Peek is already the cache-friendly read (a pure tail append); a candidate refinement is auto-dropping peek results at the next epoch unless acted on.
- Parameters (experiment conditions, not frozen guesses): commit threshold, commit target, agent/auto quota split, tail-fold exemption.

Prediction to test in round 2: output win retained (it comes from never stopping the world), fresh-input tax reduced toward native's mutation count, recall unchanged (briefs, recovery, and protection are untouched by write scheduling).

## Round 1 closure and the iteration protocol (2026-08-05)

Round 1 closed with the baseline established rather than ground to n=3: the effects are mechanism-driven with large effect sizes (a 40 percent recall gap with absent-not-wrong answers, a roughly 10x fresh/cached mix difference explained by mutation counts, a wall that reproduced at exactly stage 24 twice), the deliverable axis is ceilinged at 5/5/5 for both managed arms, and the comparison that matters next is baseline vs. mark-then-commit. Baseline holdings: rep 1 sealed for all three arms; rep 2 sealed for unmanaged (wall at stage 24 again, 1.49M chars) and pifold; native rep 2 completed 64/64 but was voided by a trailing 65th stage call after the plan finished (defect #10: a completed plan should answer "plan complete", not latch; queued for the next commit window). Native holds n=1 sealed plus two complete observational runs that agree with it.

Protocol from here (Shane, 2026-08-05): one run per iteration. Each cycle: build the change, pass the offline gates, merge and sync in a between-runs commit window, run ONE pifold-arm run on the identical pinned plan and seed, adjudicate against the baseline on five dials (per-request cache share, fresh input tokens, projection mutation count, probe recall, output tokens), decide the next lever. Scale to a multi-rep sealed round only when an iteration reaches the shape we believe. Iteration 1: mark-then-commit fold scheduling (design above).

Cross-provider validation of the cache mechanism (2026-08-05): Shane's work harness (memex, Claude Opus 5, Anthropic explicit caching) runs a 95 percent lifetime cache hit with an append-only pattern (670.8M cache read, 121.4M cache write, 6.3k uncached input over 3,132 calls), and its rare midturn collapse shows the same one-time rewrite toll (one event: 36.6k read, 232k write). Anthropic bills a mutation as cache write at 1.25x; OpenAI bills it as full-price uncached input and reports no cache-write column. Same physics, different invoice lines. The rate difference between harnesses decomposes into workload pressure (this experiment force-feeds about 3.5 window-fulls of unique material per hour, by design) times mutation policy (eager per-fold hygiene vs. lazy on-pressure eviction); only the second factor is a defect, and it is the one mark-then-commit fixes.

## Council review before iteration 1 (2026-08-05)

Before spending any run on mark-then-commit, a four-seat review examined the round-1 story, the merged build, and the iteration protocol: three in-family reviewers with single lenses (cache physics, experimental validity, design-risk triage) plus one outside pass (gpt-5.6-sol xhigh in the Pi harness, no stake in the design). Every seat was instructed to rank findings by whether they change the next run and to separate "demonstrably will not work" from "polish later". The seats converged rather than piling on; no new mechanisms were proposed.

Category A, fixed before the next run:

1. **Marks did not accumulate** (outside seat; the decisive find). Below the commit threshold, automatic selection did not exclude refs already covered by pending marks, so the ladder re-selected the same batch and duplicate marks were rejected. At commit, nearly all freeing came from the 20 percent top-up floor: expected ~14-16 epochs and ~3.7-4.1M fresh input, three times native. With accumulation fixed, commits free everything marked: ~4 epochs, ~1.4-1.8M fresh input, near native parity. One selector exclusion is the difference between the iteration reading as a win or a loss.
2. **The refold rung was unreachable in epoch mode** (triage seat): below threshold the selector returns null, at threshold the commit branch filtered the inline rung to prepared-chapter only, so expanded folds were never re-collapsed and a session could drive into the hard window fence. Fix is deleting the filter.
3. **The tail-adjacent exemption used the wrong geometry** (two seats independently): it classified by the last source message, but invalidation starts at the first. Fixed to the minimum ref index.
4. **The harness would have run immediate mode**: epoch scheduling is opt-in and nothing threaded a foldScheduling condition into the sealed manifest, and scheduling.ts was absent from the pinned file set.
5. **The comparison dials were not in the sealed evidence** (validity seat): usage was totals-only, and fold-record count measures intent, not invalidation, under mark-then-commit. Added: per-request usage series with inter-request wall clock (attributes 0 percent cached requests to mutation vs provider cache TTL), an observed-invalidation mutation counter (cacheRead falling below the prior request's total input, design-agnostic), and a think-time stall proxy from the pacing ledger (a batched commit must not quietly become the stop-the-world event the arm's headline denies). Sealed baselines get re-adjudicated with the same adjudicator so both sides of every comparison come from the same bytes.
6. Confirmed from earlier reviews, still decisive: the post-plan latch (defect #10), a state-digest key-ordering hazard in the surfacing log, and peek marks stamped as ladder-origin despite peeks being agent actions (which deflated the agent-vs-ladder ratio the agent-first story argues from).

Accuracy adjustments to the public claims: native rep 1's "three absent probe answers" trace to one omitted stage-64 response block, the same displaced-answer pattern later found in pifold rep 2 (defect #11: the adjudicator assumed answers land in the message immediately after the probe stage; the model sometimes answers one slot late, and the answers exist verbatim in the session). All sealed runs are re-adjudicated with forward-scanning extraction and re-graded before any recall number is published; rep 1 is reported descriptively, without recall causality, until the scaled round. Luna's role is predeclared: iterations on Luna order candidate designs on the mechanism dials (mutation count, cache share, fresh-input geometry); recall and output are non-inferiority checks; Sol confirms magnitude.

Deferred with promotion criteria: top-up aggressiveness (promote if voluntary folds appear and agent marks are a small minority per epoch), brief staleness at mark time (promote if a probe miss traces to an accurate-but-unhelpful brief), expand opening an epoch without top-up (instrument expand count only). No deadlock or livelock found: commit refusals drop rather than requeue, and refused agent marks are now logged per epoch so a vanished agent decision is visible.

## Iteration-1 review synthesis (2026-08-06)

Three seats (in-house mechanism/economics, in-house reliability/agent-behavior, outside gpt-5.6-sol with an open charter) plus the pooled blind grading converged on one verdict: mark-then-commit's cache mechanism is validated and scheduling tuning is DONE; what iteration 2 must buy is completion reliability under peek-heavy agents, and the highest-ranked change is a deletion, not a knob.

Grading (blind, gpt-5.6-terra, pooled packet over both Luna runs): the epoch run scored 11 correct + 1 partial on probes with 5/4/5 on all four deliverables; the immediate anchor scored 9 correct + 3 partial with one weak deliverable (1/2/0). Epoch mode is equal or better on quality, not just cheaper. The "12/12 answered" coverage number is now backed by correctness grading.

Convergent findings:

1. **Scheduling is done; the residual cost is not ours.** The economics seat reconstructed the projection ledger: only 7 of the 19 "observed mutations" are real projection rewrites (already inside the predicted 4 to 9 band); the other 12 are provider-side cache misses on pure appends (message count grew by one, no message removed, system prompt and tool shas constant, yet the request re-paid ~200k fresh). No scheduling lever can remove those. At fresh 1.0 / cached 0.1 / output 6.0 weighting, epoch mode costs 4.90M units vs native's 3.17M (1.55x); excluding the miss term it is 0.98x, parity. The outside seat independently reached "0.882 is good enough, stop tuning" with the same commit count (7 batched fold additions in the session ledger). Action: freeze refoldRatio and the commit target; instrument real rewrites separately from cache-miss observations; add per-message prefix hashing across consecutive projections to prove the misses are provider-side.
2. **The rep4 fence abort decomposes into three fixable causes, none of them "the trigger fired late."** (a) Mark starvation: the backstop fired with pending 0, agentMarks 0, freed 0; the ROI trigger alone would have had ~0.08 of window to work with and still aborted (economics seat). (b) Unbounded inflow: 21 peeks at ~62k chars each plus a status index that grew 12.6k to 86.5k chars injected ~1.24M chars of curation output between commits (vs rep3's bounded ~237k). (c) A fence 25 percent below reality: the abort fired at ~297k projected tokens against the stale 272k descriptor in the same run where the provider had just accepted 339,689 tokens; the death happened inside ~87k of real but invisible headroom (reliability seat, provider-requests.jsonl).
3. **The advisory channel was dark in all four Luna runs.** Zero advisory entries ever reached an agent; the only pressure signal any agent saw was a pressureRatio float in status payloads it requested itself. Guidance-content design is moot until arming is debugged. Related: the epoch agent's zero voluntary marks is a missing-cue problem, not suppressed instinct (it committed voluntarily once at ~0.59 pressure, then nothing recurring told it state had changed).
4. **Peek appetite is an index problem.** Agents peek whole 56-83k-char folds to recover one stage nonce or mapping. Putting the stage-to-fold mapping and next-key into briefs and status rows removes the demand instead of rationing it.

Iteration-2 build charter, ranked by the synthesis (items 1-4 are the reliability set; 5-7 ride along):

1. **Ephemeral peek** (outside seat's top open proposal, a deletion): peek output is one-model-call scope; after consumption its duplicate bytes drop from the next projection unless the agent chose pin or expand. Tail-local, so cache damage is bounded. This alone caps the inflow class that killed rep4 in epoch mode.
2. **Truthful capacity + admission control**: truthful budget accounting (serving window is 400k minus the actual output reservation, not the 272k descriptor); fence calibrated to it; peek/expand preflighted against exact stored size and truthful headroom, refused with actionable alternatives (commit first, or peek a narrower child or range), which requires the peek-narrowing affordance to ship in the same change.
3. **Mark-anywhere with retained pending marks** (lever 1): marks accepted on any span including fresh/protected; commit applies eligible marks and retains the rest; the tail-adjacent special case dissolves; refusals never silently drop.
4. **Eligible-share ROI commit trigger** (lever 2): commit fires when eligible marked mass crosses ~0.30 of the truthful window with top-up to 0.40; pressure 0.85 demoted to backstop; agent manual commit stays authoritative.
5. **Status index diet** (outside seat: paginate, do not cap): default status returns counts, headroom, pending marks, and top suggestions; the full fold tree moves behind an explicitly paged query. Stage-to-fold mapping and next-key go into briefs/status rows to kill peek demand at the source.
6. **Light the advisory channel**: debug why arming never fires; content keyed on unmarked share and headroom with freed-token estimates in tokens, not percentages.
7. **Instrumentation**: real projection-rewrite counter split from cache-miss observations; prefix-hash instrument for the provider-miss proof; fix the empty thinkTime pace mapping.

Deferred, with the economics seat's veto recorded: unmarked-share guidance as a headline lever (no voluntary marks exist yet to key on; it ships only as advisory content, item 6), top-up aggressiveness, and any further commit-count tuning. Public framing note for the write-up: the rep4 abort is safety design working on wrong inputs (a stale descriptor), and wall clock regressed 27 to 33 min with median think time up but max think time DOWN (159.7s to 136.9s), so the batched commit did not become a stop-the-world; report the wall delta without attributing it to commits.
